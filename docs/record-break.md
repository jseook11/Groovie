# 레코드 떼어내기 · 파손 (대안 기록)

상태: **채택되지 않음** · 2026-10-22 논의 기준
실제 방향: [record-crate.md](record-crate.md) — 클릭으로 레코드를 복제해 상자에 모으는 설계.

> 이 문서는 "레코드를 깨서 버린다"는 초기 아이디어의 기록이다. 이후 **파괴 대신
> 복제·보관** 방향이 선택되었고, 파손 연출은 채택하지 않았다.

관련 코드: `Interaction/OverlayController.swift`, `Interaction/VinylLayout.swift`,
`Interaction/VinylViewModel.swift`, `UI/VinylStageView.swift`, `Music/AppleMusicBridge.swift`

## 0. 한 줄 요약

싫은 곡이 나오면 고정된 LP를 노치에서 **떼어내고**, 드롭존에서 **놓으면**
낙하·파손시킨다. 파괴는 **고정(latched) 상태에서만** 가능하고, **놓는 순간** 확정된다.
파손 직후 **다음 곡으로 넘기고**, 새 트랙의 레코드를 오버레이 안에서 **갈아끼워 넣는다**.
Music 데이터(`disliked`, 재생목록)는 건드리지 않는다 — 2026-10-22 결정(8장).

## 1. 목표

- 노래를 싫어할 때의 감정을 **레코드 하나를 직접 망가뜨리는** 물리적 제스처로 표현한다.
- 기존 제스처(꺼내기 / 고정 / 탐색 / 되돌리기)의 근육 기억을 바꾸지 않는다.
- 파괴는 실수로 일어나지 않고, 일어나기 직전에 되돌릴 수 있어야 한다.
- 새로운 전역 제스처를 추가하지 않고 **상태 머신의 빈 칸 하나**를 채운다.

## 2. 현재 제스처 지도

| 상태 | ↓ | ↑ | ←→ | 클릭 |
| --- | --- | --- | --- | --- |
| 노치(idle) | 꺼내기 | — | — | 플레이어 열기 |
| 꺼내는 중(pulling) | 계속 | 취소 | — | — |
| 잡힘(grabbed, 미고정) | confirm 게이지 → 고정 | 되돌리기 | 탐색 | — |
| 대기(pending, 1초) | 고정 + 상호작용 | 되돌리기 | — | 고정 |
| **고정됨(latched)** | **비어 있음** | 되돌리기 | 탐색 | 레이블: 재생/일시정지, 본체: 닫기 |

핵심은 **고정된 상태의 ↓만 아무 의미가 없다**는 점이다
(`OverlayController.handleLatchedMouseDrag`). 파괴를 여기에 넣으면 기존 동작을
하나도 건드리지 않는다.

## 3. 설계 원칙

1. **상태가 의미를 나눈다.** 한 상태 안에서 같은 방향에 두 가지 의미를 주지 않는다.
2. **축은 조기에 확정하고 고정(sticky)한다.** 제스처 도중에 탐색 ↔ 떼어내기가
   바뀌지 않는다.
3. **파괴는 가장 늦은 단계에 둔다.** 고정 전에는 절대 파괴할 수 없다.
4. **시작점을 제한한다.** 빈 패널 공간이 아니라, 보이는 레코드 위에서 시작한
   드래그만 파괴 후보가 된다.
5. **되돌릴 수 있게 한다.** 드롭존에 들어가도 놓기 전까지는 취소 가능하고,
   존 밖에서 놓으면 제자리로 돌아온다.
6. **화면이 다음 수를 미리 보여준다.** 게이지·빈 소켓·드롭존·균열 프리뷰.

## 4. 제안 문법: "집어서 떼어내고, 놓아서 떨어뜨리기"

### 4.1 상태 추가

`VinylPhase`에 네 단계를 추가한다.

- `.detached` — 레코드가 노치에서 분리되어 포인터를 따라오는 상태
- `.falling` — 놓은 뒤 짧게 낙하하는 상태 (입력 없음)
- `.broken` — 파편이 흩어지고 정리되는 상태
- `.swapping` — 다음 트랙의 레코드가 노치로 갈아끼워지는 상태

`isEngaged`에는 포함하되, `phaseAllowsSpin`에서는 제외한다.

### 4.2 흐름

```
Idle → Pulling → Grabbed → Latched
                               │  (보이는 레코드 위에서 ↓ 20pt, |dy| > 1.5|dx|)
                               ▼
                           Detached ──(존 밖에서 놓기 / 위로 복귀)──▶ Latched
                               │  (드롭존 안에서 놓기)
                               ▼
                          Falling → Broken → Swapping → Latched
                          (짧은 낙하)  (파편)   (새 레코드 삽입)
```

`next track`은 `.falling`이 시작되는 순간 발행한다. 새 트랙 메타데이터가 도착할
때까지 빈 소켓을 유지하고, 준비되면 `.swapping`으로 새 레코드를 삽입한다.
다음 트랙이 없으면 빈 소켓을 잠깐 보여준 뒤 idle로 돌아간다.

### 4.3 판정 규칙

**시작점.** 고정 상태에서 마우스 다운 지점이 *보이는 레코드* 안일 때만 파괴 후보를
등록한다. 판정은 `거리 ≤ recordRadius` **그리고** `y ≥ emergenceInset`(노치에 가린
위쪽 반원 제외).

**축 판정(고정 상태, 파괴 후보 등록 후).**

| 입력 | 판정 |
| --- | --- |
| 시작점이 레코드 밖 | 기존 동작만. 파괴 없음 |
| ↑ 우세 | 기존 닫기/복귀 |
| ←→ 우세 (`abs(dx) ≥ 3`) | 탐색. 이후 세로로 꺾어도 파괴로 전환하지 않음 |
| ↓ 우세 (`dy ≥ 20` 이고 `dy > abs(dx) × 1.5`) | 떼어내기. 이후 가로로 꺾어도 탐색으로 전환하지 않음 |
| 이미 `.detached` | 레코드가 포인터를 2D로 따라옴. 탐색 없음 |

**드롭존.** 떼어낸 레코드가 노치에서 일정 거리(출발값: 고정 위치 + 170pt) 아래로
내려가면 점선 드롭존이 보이고, 레코드에 균열 프리뷰와 햅틱이 붙는다.

**확정.** 드롭존 안에서 **놓으면**(mouse-up) `.falling`으로 간다. 존 밖에서 놓으면
`latched` 위치로 스프링 복귀한다. 존을 넘었다가 다시 위로 끌어오면 프리뷰가 풀린다.

### 4.4 열린 선택: 연속 오버풀

confirm 게이지가 차서 latch된 뒤 **같은 드래그를 계속 아래로** 당겨 드롭존까지
이어가는 것을 허용할지 여부.

- **허용 안 함(1차 권장)**: latch 시점에 드래그의 목적이 끝난다. 손가락과 레코드가
  떨어져 있어 시각적 연결이 어색하고, 오버슈트로 파괴될 위험이 있다.
- **허용**: "한 번에 낚아채서 던지는" 감정적 동작은 좋지만, latch 이후 레코드가
  포인터를 따라가기 시작하는 순간의 점프/지연을 따로 설계해야 한다.

### 4.5 수치 출발값 (튜닝 전)

- 떼어내기 게이트: 아래로 20pt, `dy > 1.5 × |dx|`
- 드롭존 시작: 고정된 레코드 중심 + 170pt 아래
- 파괴 연출은 화면 전체 낙하가 아니라 **현재 스테이지 오버레이 안에서** 끝낸다.
  임시 창은 190 → **260~300pt** 정도만 확장한다.
- 복귀 스프링: 기존 `collapseStiffness`/`collapseDamping` 재사용 또는 별도 상수

## 5. 피드백

| 시점 | 시각 | 촉각/청각 |
| --- | --- | --- |
| 떼어내기 | 레코드가 노치에서 분리, 빈 소켓, confirm 게이지 숨김 | 약한 햅틱 |
| 드롭존 진입 | 점선 존, 균열 프리뷰, 레코드 톤 변화 | 중간 햅틱 |
| 놓기(존 안) | 스테이지 안에서 짧게 낙하·회전, 충격 후 파편 | 강한 햅틱 + 짧은 파손음 |
| 놓기(존 밖) | 제자리로 스프링 복귀 | 약한 햅틱 |
| 새 레코드 삽입 | 빈 소켓에서 다음 트랙 레코드가 나와 고정 위치에 안착 | 약한 햅틱 |

드롭존 라벨은 로컬라이제이션이 필요하다. 기존 `overlayPullToLock`과 같은 방식으로
`overlayDropToBreak` 같은 키를 en/ko에 추가한다.

## 6. 히트 영역과 창

- **입력 영역**은 지금과 동일하다. idle에서는 노치 스트립(`StageGeometry.idleFrame`),
  스테이지가 열려 있는 동안에는 펼쳐진 패널 전체(`expandedFrame`).
- **마우스 캡처**: AppKit은 mouseDown이 시작된 창에 드래그 이벤트를 계속 보낸다.
  포인터가 현재 300×190 창 밖으로 나가도 좌표는 들어오므로, 떼어내기 판정은
  창 크기와 무관하게 가능하다.
- **렌더링**: 파괴와 교체 연출은 화면 전체로 떨어뜨리지 않고 **스테이지 오버레이
  안에서** 끝낸다. 떼어내기·낙하 동안만 창을 세로로 조금(190 → 260~300pt) 확장하고,
  낙하 중에는 `ignoresMouseEvents = true`로 다른 앱/메뉴 클릭을 막지 않는다.
  끝나면 idle 프레임으로 복귀한다.
- **호버**: 확장 중 들어오는 `mouseEntered/Exited`는 기존 phase 가드로 무시한다.
- **레이블**: 기존 42pt 히트 영역(`labelRadius + labelHitSlop`)과 클릭 =
  재생/일시정지 규칙은 유지한다. 레이블에서 시작한 드래그도 축에 따라 탐색/떼어내기.

### 구현 시 함정

- `syncFromMusic`의 `abortActiveGesture()`가 **스킵으로 트랙이 바뀌는 순간**
  `.falling/.broken/.swapping`을 접어버린다. 이 상태들은 예외 처리한다.
- `pendingConfirmUntil` 만료 검사와 `handleScroll`의 phase 가드에 새 상태를 추가한다.
- `tick`은 `.grabbed`에서 타이머를 멈추는 최적화가 있다. 떼어내기/낙하 중에는
  타이머를 유지한다.
- `finishLostDrag`(mouse-up 유실)에서 `.detached`는 파괴가 아니라 복귀 처리한다.
- `next track` 직후 새 트랙 메타데이터/아트워크가 늦게 올 수 있다. `.broken`에서
  새 트랙이 준비될 때까지 빈 소켓을 유지하고, 타임아웃(예: 1.5초) 뒤에는 idle로
  떨어진다. 다음 트랙이 없을 때의 빈 소켓도 같은 경로로 처리한다.
- 파손 시 재생 상태: 재생 중이었으면 다음 곡도 재생, 일시정지였으면 일시정지 유지가
  덜 놀랍다. `next track`의 실제 동작을 확인하고 play/pause를 명시적으로 복원한다.
- `DemoMusicService`와 `AppleMusicService` 양쪽에 `skipToNext()`를 구현한다.
- `phaseAllowsSpin`과 `pointerOwnsAngle`을 새 상태에 맞게 정리한다.
- 파편 렌더링은 기존 `RotatingDiscView`처럼 CALayer 기반으로 두어 60Hz SwiftUI
  갱신을 피한다.

## 8. Music.app 연동: "싫어요"와 재생목록/이전 곡

### 8.1 확인한 사실

검증 환경: macOS 26.7.1, Music 1.6.6.

- Music 스크립팅 사전(`com.apple.Music.sdef`)에는 트랙의 `disliked`(boolean),
  `favorited`(boolean), `rating`(integer)이 **쓰기 가능한 속성으로 선언**되어 있다.
  `track` 클래스는 `library.read-write` 접근 그룹(rw)을 가진다.
- `delete` 명령은 "요소를 삭제"하는 일반 명령으로 존재하고, `user playlist`는
  `library.read-write`(rw)다.
- `previous track` 명령의 설명은 "**현재 재생목록에서** 이전 트랙으로 돌아간다"이다.
- 실제 Apple Music 스트리밍 재생 중에는 현재 트랙이 `URL track`이고,
  `container`가 `source`("Scripting", kind `iTunes Store`)이며,
  **`current playlist`는 `-1728` 오류로 가져올 수 없다.**
  즉 스트리밍 재생에는 스크립트로 조작할 재생목록 객체가 노출되지 않는다.
- 로컬 라이브러리/사용자 플레이리스트 재생에서는 `current playlist`가 동작할
  가능성이 있으나, 별도 검증이 필요하다.

### 8.2 하고 싶은 일별 가능성

| 하고 싶은 일 | 가능성 | 방법과 한계 |
| --- | --- | --- |
| 다음 곡으로 넘기기 | **가능** | `next track` |
| "싫어요" 표시 | **선언상 가능** | `set disliked of current track to true`. 스트리밍/URL 트랙에서 실제 반영되는지는 검증 필요. 추천에 영향을 주지만 **현재 큐/히스토리를 바꾸지는 않는다** |
| 사용자 플레이리스트에서 제거 | **조건부 가능** | 현재 재생 소스가 `user playlist`일 때만. persistent ID로 항목을 찾아 플레이리스트 범위에서 `delete`. 사용자 데이터를 영구 변경하므로 확인 필요 |
| Apple Music Up Next 큐에서 제거 | **불가** | 큐 편집 API가 없다 |
| 재생 기록(히스토리)에서 제거 | **불가** | 히스토리 API가 없다 |
| "이전 곡"이 그 곡으로 안 돌아가게 | **보장 불가** | `previous track`은 Music 내부 큐/히스토리를 따른다. 스크립트로 그 스택을 편집할 수 없다 |
| Umak 자체 차단 목록 | **가능(자체 구현)** | 곡이 시작되면 자동 스킵. 단, Music의 이전 버튼 자체를 막지는 못하고 잠깐 재생될 수 있음. 별도 opt-in 기능 |

### 8.3 위험

- **`set disliked`는 사용자의 Apple Music 프로필/추천 데이터를 바꾼다.**
  묻지 않고 자동으로 하면 안 된다. 이번 설계에서는 쓰지 않기로 했다(8.4).
- **`delete`는 사용자 플레이리스트를 영구 수정한다.** 역시 이번 설계에서는
  자동 삭제하지 않는다(8.4).
- `delete current track`처럼 **라이브러리 트랙을 직접 지정하면 라이브러리에서
  곡이 삭제될 수 있다.** 플레이리스트 범위의 항목 참조로만 삭제해야 한다.
- System Events로 "Up Next에서 제거" UI를 클릭하는 방식은 Accessibility 권한이
  필요하고 Music UI 변경에 취약하다. 채택하지 않는다.

### 8.4 결정 (2026-10-22)

- **파손 = `next track`.** 별도 설정 없이 항상 다음 곡으로 넘긴다.
- **`disliked`는 쓰지 않는다.** 사용자의 Apple Music 프로필/추천 데이터를 바꾸는
  동작이라 "너무 파괴적"이라는 판단. 8.2의 쓰기 가능성은 기록만 남긴다.
- **재생목록 삭제도 하지 않는다.** 사용자 데이터 영구 변경 + 소스별 동작 불확실.
- "이전 곡"이 그 곡으로 돌아가는 것은 **공개 API로 막을 수 없다**고 문서화한다.
  Umak 자체 차단 목록도 파손 제스처와 결합하지 않는다.
- Music 쪽에서 하는 일은 `next track` 하나뿐이다. 나머지는 전부 Umak 오버레이
  안의 시각 연출(파손 → 새 레코드 갈아끼우기)로 해결한다.

## 9. 결정

### 확정

- 파손 후 재생: **다음 곡** (`next track`)
- 싫어요 표시: **하지 않음**
- 재생목록 제거: **하지 않음**
- 파손 후 레코드: **다음 트랙 레코드를 오버레이 안에서 갈아끼움**

### 남은 결정

1. **파괴 가능 상태**: 고정(latched)에서만(권장) vs. confirm 직후 계속 당기면 한 동작.
2. **확정 방식**: 드롭존에서 놓아서 확정(권장) vs. 선을 넘는 순간 자동 파손.
3. **파손 연출 위치**: 스테이지 오버레이 안(권장, 창 확장 최소) vs. 화면 아래로 크게 낙하.
4. **새 레코드 삽입 타이밍**: 파편이 흩어진 뒤 vs. 파편과 교차.

## 10. 구현 순서와 예상

1. `.detached` 상태 + 축 분류기 + `SelfChecks` (시각 효과 없이)
2. 떼어내기 → 포인터 추적 → 드롭존 프리뷰 → 복귀 스프링
3. 낙하 + 파편 렌더링 + 사운드
4. `next track` + 새 레코드 교체 연출, 데모 시퀀스, README·로컬라이제이션

예상: 1번 0.5일, 2번 0.5~1일, 3번 0.5~1일, 4번 0.5일 → **총 2~3일**.
파편을 최소 버전(원판 회전·축소·페이드 + 균열선)으로 두고 창을 크게 확장하지
않으면 1.5~2일.

## 11. 테스트와 데모

- **분류기 단위 검사**: 레코드 밖 시작, 가로 우세, 세로 우세, sticky 전환 금지,
  latch 전 파괴 불가, 존 경계, release 위치.
- **물리 검사**: 낙하 위치/속도 적분, 창 경계 클램프, 최대 시간 후 종료.
- **수동 확인**: 노치/비노치 화면, 마우스업 유실, 파손 중 트랙 변경(스킵),
  풀스크린 앱 위, 멀티 디스플레이, 스크롤 세션과의 상호작용.
- **데모**: 꺼내기 → 고정 → 떼어내기 → 드롭존 → 파손 → 새 레코드 교체.
- **Music 스크립트 검증**: 폐기 가능한 사용자 플레이리스트로
  `current playlist` / `delete` / `previous track` 동작을 사용자 동의 하에 확인.
  스트리밍 재생에서는 `current playlist`가 없음을 재확인.

## 12. 비목표

- Music의 Up Next 큐·재생 히스토리 직접 편집
- "싫어요"가 추천/재생에 반영된다고 보장하기
- 모든 재생 소스(스트리밍/라디오/공유)에서 재생목록 제거 지원
- 두 손가락 스크롤로 파괴
- `disliked` 쓰기, 재생목록 삭제 (2026-10-22 제외 결정)
- 사용자 확인 없는 데이터 변경
